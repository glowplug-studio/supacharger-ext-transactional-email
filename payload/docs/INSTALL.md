# Install transactional email

1. Use Core containing `src/supacharger/extensions/services.cjs`, the common email schema and the `core_service_bindings` migration.
2. Set `PROJECT_NAMESPACE` to a stable lowercase deployment identifier (1–20 characters), and select `supacharger-ext-transactional-email` for `CORE_SERVICES.transactional_email.provider`.
3. Keep the extension config under `src/app/(project)/(extensions)/(sc_extensions)/(transactional-email)/supacharger-ext-transactional-email.config.ts`. Select `brevo/api`, `resend/api`, `mailgun/api` or `smtp/smtp`. Brevo supports hosted templates only; SMTP requires rendered content. Resend and Mailgun accept either.
4. Run the source package's `scripts/prepare.mjs` against the application and a migration created with `supabase migration new`. Review the generated package and SQL. Install the reviewed prepared directory through Core's local extension installer. The release ZIP download path is separate.
5. Set namespaced credentials in the Edge secret store. API adapters read `<NAMESPACE>_EXT_TRANSACTIONAL_EMAIL_API_KEY`. Template keys map to `<NAMESPACE>_EXT_TRANSACTIONAL_EMAIL_TEMPLATE_<KEY>`. Mailgun may additionally use `<NAMESPACE>_EXT_TRANSACTIONAL_EMAIL_TEMPLATE_VERSION_<KEY>` for an explicit template version. The worker reads `<NAMESPACE>_EXT_TRANSACTIONAL_EMAIL_WORKER_SECRET` (at least 32 characters). SMTP uses `_SMTP_USER` and `_SMTP_PASSWORD` instead of an API key.
6. Apply Core SQL first, then the generated extension migration. Dispatch starts disabled. Register trusted private product resolver functions where messages require eligibility rechecks; the callback accepts `{message, context}` and returns an eligible common message or null.
7. Deploy the generated worker with platform JWT verification disabled. Its separate bearer secret protects every command. Create namespaced Vault entries `<namespace>_ext_transactional_email_worker_url` and `_worker_secret`. The URL must identify the generated HTTPS Supabase worker.
8. Call `check`, reconcile any old jobs and dispatchers, then explicitly enable the private settings row. One cron recovery job and post-commit wake-up use the same queue.

The public envelope is `{id, to: {email, name?}, content, replyTo?}`. Template content is `{kind: 'template', key, variables}`; rendered content is `{kind: 'rendered', subject, html?, text?}` with at least one body. One UUID represents one recipient and immutable message content. Repeat enqueue is idempotent; different content with the same ID is rejected. Internal context is separate and is never sent to a provider.

The worker accepts POST JSON `{action: 'check'}`, `{action: 'process', ids?: string[]}` or `{action: 'retry', ids: string[]}`. Commands are privileged; they do not accept messages. Counts distinguish accepted, retryable, blocked, uncertain and failed. Accepted means provider acknowledgement only. Uncertain outcomes require investigation and are never automatically resent. Retryable failures use bounded exponential delays; eight attempts exhaust retries. Selected retries are limited to repairable blocked states and repeat template and privacy checks.

SMTP uses authenticated TLS with certificate verification, a pinned Nodemailer dependency and bounded timeouts. Hosted Supabase blocks ports 25 and 587. Use a supported implicit TLS port (normally 465); the selected relay must be verified in the deployment runtime. Never treat source support as evidence of live delivery testing.

Provider selection is compiled into the prepared worker. Changing it requires another preparation and deployment with an explicit pending-job decision. The generated SQL and worker source show the installed namespace, secret names and selected provider import. Config stays developer-owned; installed source and generated output are extension-managed. Never rewrite applied migrations.
